# Deployment

Free-tier topology: **Supabase** (PostgreSQL) → **Render** (FastAPI backend) → **Vercel**
(React frontend), with **GitHub Actions** as the CI gate.

| Piece    | Host           | Config in repo          |
| -------- | -------------- | ----------------------- |
| Database | Supabase       | —                       |
| Backend  | Render         | `render.yaml`           |
| Frontend | Vercel         | `frontend/vercel.json`  |
| CI       | GitHub Actions | `.github/workflows/ci.yml` |

Deploy in that order — the backend needs the database URL, and the frontend needs the
backend URL.

---

## 1. Database (Supabase)

1. Create a project at [supabase.com](https://supabase.com). Save the database password.
2. Open **Connect** and copy the **Session pooler** connection string. It looks like:

   ```
   postgresql://postgres.<project-ref>:<password>@aws-0-<region>.pooler.supabase.com:5432/postgres
   ```

   Use the *session* pooler (port 5432), not the direct connection and not the transaction
   pooler:
   - the **direct** connection is IPv6-only and Render has no IPv6 egress, so it will hang;
   - the **transaction** pooler (port 6543) drops prepared statements, which psycopg 3 relies on.

3. URL-encode any special characters in the password (`@` → `%40`, `#` → `%23`, and so on).

`postgresql://` is rewritten to `postgresql+psycopg://` in `app/core/config.py`, so paste the
string exactly as Supabase gives it.

Schema creation is handled by Alembic on each backend boot — there is nothing to run by hand.

## 2. Backend (Render)

1. **New → Blueprint**, point it at this repository. Render reads `render.yaml` and creates the
   `ai-creative-copy-agent-api` web service on the free plan.
2. Fill in the env vars marked `sync: false` (Render prompts for each):

   | Variable             | Value                                                 |
   | -------------------- | ----------------------------------------------------- |
   | `DATABASE_URL`       | the Supabase session-pooler string from step 1         |
   | `PUBLIC_BASE_URL`    | this service's URL, e.g. `https://<name>.onrender.com` |
   | `CORS_ORIGINS`       | the Vercel production URL (set after step 3)           |
   | `FRONTEND_BASE_URL`  | the same Vercel URL                                    |
   | `AI_PROVIDER`        | `gemini` (or `mock` to run without credentials)        |
   | `GEMINI_API_KEY`     | key from Google AI Studio                              |
   | `GEMINI_FLASH_MODEL` / `GEMINI_PRO_MODEL` | model ids from AI Studio          |
   | `IMAGE_PROVIDER`     | `mock`, `gemini`, or `stability` (+ `STABILITY_API_KEY`) |
   | `GROUNDING_ENABLED`  | `true` or `false` — never blank                        |
   | `GROUNDING_PROVIDER` | `none`, `mock`, `gemini` or `tavily` (+ `TAVILY_API_KEY`) |
   | `EMAIL_PROVIDER`     | `resend` (+ `RESEND_API_KEY`, `EMAIL_FROM`) or `console` |
   | `GOOGLE_CLIENT_ID`   | empty to disable Google sign-in; see below              |
   | `GOOGLE_DEFAULT_ROLE`| `admin`, `marketer` or `viewer` — never blank          |

   `JWT_SECRET_KEY` is generated by Render. `APP_ENV=production` is set in the blueprint, which
   makes the app refuse to start if `AUTO_CREATE_TABLES` or `SEED_ON_STARTUP` is left on.

   **Only the credential fields may be left empty** — `GEMINI_*`, `STABILITY_API_KEY`,
   `TAVILY_API_KEY`, `RESEND_API_KEY`. A blank credential reads as "not configured", but the
   provider switches above are strict choices and an empty value fails startup with a raw
   validation error.

   A provider selected without its key is reported per generation: the run fails with
   `AI_NOT_CONFIGURED` naming the missing variable, rather than taking the service down.

3. `CORS_ORIGINS` must list the exact Vercel origin with no trailing slash. Vercel preview
   deployments get their own hostnames and will *not* match — add them individually if you want
   previews to reach the API.

### Google sign-in (optional)

1. In [Google Cloud Console](https://console.cloud.google.com) → **APIs & Services →
   Credentials**, create an **OAuth client ID** of type *Web application*.
2. Add the Vercel production URL as an **Authorised JavaScript origin** — origin only, no path,
   no trailing slash. No redirect URI is needed: the frontend uses Google Identity Services and
   posts the resulting ID token to `POST /auth/google`.
3. Set `GOOGLE_CLIENT_ID` on Render. Nothing needs rebuilding on Vercel — the login screen reads
   the client id from `GET /auth/options` at runtime and shows the button once it is present.
   (`VITE_ENABLE_GOOGLE_LOGIN` only labels a row on the Settings page; set it to `true` as well
   so that display is not misleading.)

The client id is public by design — it identifies the application to Google and is visible in
every browser request. There is no client *secret* in this flow.

> **`ALLOW_REGISTRATION=false` does not close Google sign-in.** The register endpoint honours that
> switch; `GoogleAuthService` does not, so a first-time Google sign-in still provisions an account
> with `GOOGLE_DEFAULT_ROLE`. With Google enabled on a public URL, anyone holding a Google account
> can obtain that role. Unlike the register endpoint, the role comes from configuration rather
> than the request, so it cannot be escalated to `admin` — but the account is still created.
> Set `GOOGLE_DEFAULT_ROLE=viewer` if you want the open door to be read-only.

### Free-tier limits that will bite

- **Cold starts.** The instance sleeps after ~15 minutes idle; the next request takes ~50s.
  A generation request arriving during wake-up may exceed the frontend's timeout.
- **Interrupted runs.** A generation executes as an in-process background task, so a sleep or
  redeploy mid-run abandons it. The app fails any generation left `pending` or `running` when it
  next starts, which is why the status screen reports a restart instead of polling forever.
- **Ephemeral disk.** Generated images written to `MEDIA_DIR` are lost on every restart and
  redeploy, so image URLs from earlier sessions will 404. Fine for a demo; a real deployment
  needs object storage behind the media layer.
- **512 MB RAM.** Enough for this service, but leaves no headroom for concurrent generations.

## 3. Frontend (Vercel)

1. **Add New → Project**, import the repository, set **Root Directory** to `frontend`.
   `vercel.json` supplies the framework, build command, and the SPA rewrite that React Router
   needs for deep links.
2. Set environment variables:

   | Variable                   | Value                                          |
   | -------------------------- | ---------------------------------------------- |
   | `VITE_API_BASE_URL`        | `https://<render-service>.onrender.com/api/v1` |
   | `VITE_APP_NAME`            | `AI Creative Copy Agent`                       |
   | `VITE_ENABLE_DEMO_DATA`    | `false` for a real deployment                  |
   | `VITE_ENABLE_GOOGLE_LOGIN` | `false` unless an OAuth client is configured   |

3. Deploy, then go back to Render and set `CORS_ORIGINS` and `FRONTEND_BASE_URL` to the Vercel
   production URL.

### Cross-site cookies

The refresh token is an HttpOnly cookie, and `vercel.app` → `onrender.com` is a cross-site
request. The blueprint therefore sets `COOKIE_SECURE=true` and `COOKIE_SAMESITE=none`; without
both, browsers drop the cookie and every session ends at the first token refresh.

## 4. CI/CD

`.github/workflows/ci.yml` runs on every push to `main` and every pull request:

- **backend** — `ruff check .` then `pytest` (SQLite, mock model runtime, no network)
- **frontend** — `npm run lint`, `npm run test`, `npm run build`

Deployment itself is handled by Render's and Vercel's native GitHub integrations, which redeploy
on push to `main`. To make CI a real gate, add the `backend` and `frontend` checks as required
status checks in **Settings → Branches → Branch protection rules** — otherwise a red build still
ships.

Both platforms are free for this usage: Actions is free on public repos (2,000 min/month on
private), Render's free web service and Vercel's Hobby plan cover the rest.

## 5. First run

Production starts with an empty database beyond the schema and the content rules inserted by
migration `0003`. There are no seeded users — `SEED_ON_STARTUP` is off, and it seeds
known-password demo accounts, so never enable it here.

1. Load the reference data — brands, products, audience segments, CTA rules and templates. From
   `backend/` with the virtualenv active, pointed at the Supabase database:

   ```bash
   DATABASE_URL='<supabase-session-pooler-url>' python -m app.database.seed --taxonomy-only
   ```

   This creates no accounts, prints no passwords, and leaves the schema to Alembic. Run it from
   your machine: Render's free plan has no shell. Re-running it changes nothing, and you can skip
   it entirely if you would rather build the taxonomy by hand in the admin screens.
2. Register the first account through the UI. Anything else — further brands, products or content
   rules — is managed from the admin screens.
3. **Then set `ALLOW_REGISTRATION=false` on Render.** The register endpoint accepts a `role`
   field from the client, so while registration is open anyone can create themselves an **admin**
   account. Closing registration is the only thing standing between a public URL and full admin
   access.
